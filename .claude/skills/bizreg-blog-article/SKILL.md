# BizReg — стандарт блог-статьи

Любая статья в `content/blog/` должна соответствовать этому стандарту. Цель: дорогой, доверительный, уникальный лонгрид под YMYL-нишу (юр/налоги/бизнес в Узбекистане). **Каждая статья — уникальна по контенту И по дизайну.**

## 0. Главное правило — УНИКАЛЬНОСТЬ И РАЗНЫЙ ДИЗАЙН
- **Никаких клонов.** Нельзя брать предыдущую статью и менять слова — это убивает SEO и доверие.
- **Каждая статья выглядит по-разному:** меняй набор и ПОРЯДОК блоков, типы инфографики, структуру разделов, hero-фото, акценты.
- **Минимум один уникальный визуальный элемент на статью** — своя инфографика/схема (можно отдельный SVG-компонент под тему), нестандартная компоновка раздела, своя таблица-сравнение и т.п.
- Контент уникален по сути: разный угол, своя глубина, свои примеры/данные под тему.
- Перед написанием — посмотри уже существующие статьи и сделай НЕ так, как они.

### 0.1 Жёсткие правила по фото (из ревью заказчика)
- **НИ ОДНО фото не повторяется между статьями.** Каждый файл изображения используется только в одной статье (ru+en одной статьи могут делить фото — это одна статья). Аудит блокирует повтор.
- **Hero должен ПРИНЦИПИАЛЬНО отличаться** от hero соседних статей — не «ещё один похожий кадр», а другая **визуальная категория**: пейзаж/город ≠ финансовый флэтлей ≠ офис/люди ≠ tech/код ≠ документы ≠ абстракция. Две статьи подряд не должны «сливаться».
- Перед вставкой фото — **скачать и посмотреть глазами** (Read); проверить, что оно не дублирует уже использованные и не относится к чужой стране (напр. налоговые формы США для статьи про УЗ — нельзя).

### 0.2 Длина — РАЗНАЯ у каждой статьи
- **Никогда не меньше 1200 слов** на язык.
- **Каждая статья — другого объёма**, не делай все одинаковыми: чередуй цель ~1300 / 1500 / 1700 / 2000 слов (под глубину темы). Две соседние статьи не должны быть одной длины.
- Глубину набирай по делу: примеры, пошаговые разборы, частые ошибки, ответственность/сроки, сравнения, кейсы, больше FAQ — без воды.

### 0.3 Акцентная тема (чтобы дизайн реально отличался)
- У каждой статьи свой **`accent`** во frontmatter: `teal | indigo | amber | emerald | violet | rose | sky`. Он прокрашивает стат-карточки, callout-tip, CompareCard, CTA, ссылки, FAQ, «Главное».
- **Соседние/смежные статьи — разные accent** (не два teal подряд). Подбирай цвет под тему (напр. налоги — indigo/sky, IT — violet, юр.адрес — amber/emerald).
- **`heroStyle`** во frontmatter меняет компоновку шапки: `photo` (фото на всю ширину + тёмный оверлей), `split` (фото справа + акцентная панель слева), `accent` (цветная плашка-градиент без большого фото). У соседних статей — разный heroStyle.
- Дополнительно варьируй: набор и порядок блоков, наличие TOC, уникальную инфографику. Цель — чтобы две статьи **не выглядели одинаково**.

## 1. Файлы и локали
- `content/blog/<slug>.ru.mdx` + `content/blog/<slug>.en.mdx` (обе обязательны; `zh` — по желанию).
- `slug` — латиница, по ключевому запросу (см. `BezReg_SEO/01_keyword_research/keyword_core_clean.csv`).

## 2. Frontmatter (обязательные поля)
```yaml
title:           # ≤65 симв., содержит целевой ключ
description:     # 50–160 симв.
keyword:         # ЦЕЛЕВОЙ КЛЮЧ статьи (1 на статью) — под него title/lead/H2; своя формулировка для ru и en, совпадающая с заголовком
image:          # /blog/<hero>.jpg — фото-герой (он же OG)
imageAlt:       # осмысленный alt
datePublished:  # YYYY-MM-DD
dateModified:   # YYYY-MM-DD
factsCheckedOn: # дата сверки фактов
cluster:        # код кластера C1–C13 (даёт тег карточки на /blog; см. §7 и lib/tags.ts)
author:         # ivan | elena | karima (по теме, см. ниже)
ctaPath:        # маршрут на профильную страницу (пока "/", позже — money-страница)
ctaLabel:       # текст CTA
faq:            # ≥3 пары q/a (идут и в FAQPage schema)
sources:        # ≥1, минимум один официальный (lex.uz / soliq.uz / it-park.uz)
```

## 2.1 SEO-оптимальность (проверяется автоматически, есть ПОРОГ)
`npm run audit:blog` считает пер-статейный **SEO-score 0–100**; **<70 → ERROR (статья на доработку, push заблокирован), цель ≥85.** Составляющие:
- **Ключ (`keyword`) в `title`** (20) и в **первом абзаце `<Lead>`** (15). title и keyword для en — на английском, формулировки совпадают.
- **≥3 внутренних ссылки** на другие статьи блога (20) + статья **НЕ «сирота»** — на неё ссылается ≥1 другая статья (15). Практика: в конце добавляй блок «## Похожие статьи / ## Related articles» с 3–4 ссылками на родственные статьи кластера (анкор = заголовок целевой статьи). **ru → `/blog/<slug>`, en → `/en/blog/<slug>`** (локале-префикс обязателен для en/kk/uz/zh).
- Объём ≥1200 слов (10), ≥5 `<Faq>` в теле (5), `<Lead>` (5), `description` 50–160 (5), `title` ≤65 (5).
- Совет (не в баллах): полезно дать ключ хотя бы в одном H2 — но без переспама, естественно.

## 2.2 AEO — оптимизация под ИИ-ответы (проверяется аудитом, ERROR при отсутствии)
ИИ-поиск (ChatGPT/Perplexity/AI Overviews/Яндекс Нейро) цитирует извлекаемые, структурированные ответы. Обязательно:
- **`<KeyTakeaways>` (TL;DR)** с конкретными числами/фактами — ИИ берёт его как готовую выжимку. (аудит: ERROR, если нет)
- **≥1 H2-вопрос** — подзаголовок в форме реального вопроса с «?» (напр. «Сколько стоит открыть ООО в Узбекистане?», «Какая ставка НДС в 2026?»). Делай 2–3 таких, естественно, с ключом. (аудит: ERROR, если нет ни одного `## …?`)
- **BLUF:** первое предложение `<Lead>` и каждого раздела — прямой ответ-факт, потом детали (ИИ выдёргивает первую фразу).
- **Конкретика вместо хеджа:** где факт подтверждён в Tier-1 — дай число прямо (хедж «уточняйте» оставляй только для реально неподтверждённого).
- HowTo-schema для пошаговых статей и `/llms.txt` генерируются автоматически (шаги берутся из `<Steps>`); просто используй блок `<Steps><Step title="…">` для процессов.

## 3. Автор по теме (E-E-A-T, реальные партнёры)
- **ivan** (Иван Каратаев, управляющий партнёр) → регистрация компании, бизнес, релокация, выход на рынок.
- **elena** (Елена Васюкова, учёт и налоги) → налоги, НДС, бухгалтерия, отчётность.
- **karima** (Карима Тазиева, недвижимость) → юр.адрес, офис, коворкинг, недвижимость.
Подпись автора, регалии, фото, блок «кто мы», Person-schema — рендерятся шаблоном `ArticleLayout` автоматически. Не выдумывай других авторов.

## 4. Точность фактов (YMYL)
- Используй скил **`uz-legal-sourcing`**: все цифры/ставки/сроки — из Tier-1 (lex.uz, soliq.uz, it-park.uz, cbu.uz) + дата.
- **Сначала проверь новости об изменениях** (последние 6–12 мес) — чтобы не пропустить свежие правки (напр. НДС с 1 июня 2026). Новость = сигнал; цифру бери только после подтверждения в Tier-1.
- **Никогда не выдумывай ставки/числа.** Нет подтверждения — не пиши цифру, дай ссылку на первоисточник.

## 5. Визуальные блоки (доступны в MDX)
`Lead`, `Callout` (info/tip/warning/note), `StatGrid`+`Stat`, `Steps`+`Step`, `CompareGrid`+`CompareCard`, `KeyTakeaways`, `ProsCons`+`Pros`+`Cons`, `IconGrid`+`Feature` (icon: building/doc/bank/wallet/shield/rocket/globe/scale), `Faq`, `Figure`, `InlineCta`, `CtaBox`, `HeroArt`.
- Markdown-таблицы работают (remark-gfm).
- Для уникальности можно добавлять **свои** компоненты/SVG в `components/blog/` под конкретную статью.

## 6. Обязательные требования к контенту
- **Фото-герой** (`image`) + **минимум 2–3 фото в тексте** (`<Figure>`).
  - Фото — **аутентичные**: восточноевропейская/центральноазиатская внешность, реальная офисная среда (не «интернационал-сток»). Источники: фото клиента → AI по согласованию → бесплатный Pexels/Unsplash (`images.pexels.com`/`images.unsplash.com`, НЕ `plus.unsplash.com`). **Скачивай в `public/blog/` и СНАЧАЛА посмотри глазами** (Read), потом ставь.
  - **Фото не повторяются между статьями** (см. 0.1); **hero — принципиально другой категории**, чем у соседних статей.
- **Много текста** — лонгрид (**≥1200 слов**, см. 0.2), реальная польза, без воды.
- **Инфографика** — шаги/стат-карточки/иконки/сравнения + ≥1 уникальный визуал под тему.
- **Много FAQ** — ≥5 `<Faq>` в теле (и ≥3 в frontmatter для schema).
- **Inline-CTA по тексту** — 2–3 `<InlineCta>` в разных местах (не только `<CtaBox>` внизу).
- `<Lead>` в начале.

## 7. Карточка статьи на /blog (оформление при публикации)
На странице `/blog` каждая статья — карточка с поиском и фильтром по тегам. Чтобы карточка отображалась правильно, при публикации обязательно:
- **Обложка** — `image` (качественный hero) + осмысленный `imageAlt`. Без `image` карточка будет с пустой заглушкой.
- **Тег категории (ОБЯЗАТЕЛЬНО).** `cluster` должен начинаться с распознаваемого кода **C1–C13** (источник меток — `lib/tags.ts`):
  `C1` Регистрация · `C3` Иностранное предприятие · `C4` IT Park · `C5` Юр. адрес · `C6` Бухгалтерия · `C7` Налоги · `C8` Разрешение на работу · `C9` Банковский счёт · `C10` Лицензии · `C11` Персонал · `C12` ВНЖ и релокация · `C13` Платежи и ВЭД.
  Суффикс допустим (`C1xГЕО`, `C4ITPark`), берётся префикс `CN`. Из кода строится **бейдж-тег** на карточке и по нему работает **фильтр/поиск** в разделе. Кластер без валидного C-кода → карточка без тега (**аудит блокирует push**).
- **Описание карточки** — `description` (50–160) выводится под заголовком; пиши осмысленно, не обрезком.
- **Дата обновления** — на карточке показывается «Обновлено: `dateModified`» (иначе `datePublished`). **При каждой правке статьи обновляй `dateModified` на текущую дату** — иначе на карточке будет старая дата.

## 8. Тех-SEO (даёт шаблон, проверь что не сломал)
canonical, hreflang (ru/en/x-default), OG/Twitter image, Article+Person+FAQ+Breadcrumb schema, TOC по h2, время чтения, sitemap+lastmod, IndexNow. Один `<h1>` (заголовок в hero) — в тексте только `##`/`###`.

## 9. Рабочий процесс
1. Выбрать тему/slug по keyword research; назначить автора по теме.
2. **Проверить свежесть: поиск новостей об изменениях** по теме за 6–12 мес (`firecrawl_search`, можно `sources: news`: «<тема> Узбекистан 2026 изменения / новая ставка / с какого числа»). Найденные изменения → **подтвердить в Tier-1** (lex.uz/soliq.uz) и указать с датой; без подтверждения не публиковать. Затем собрать остальные факты через `uz-legal-sourcing`.
3. Подобрать и **посмотреть** фото (hero + 2–3), скачать в `public/blog/`.
4. Написать `ru` и `en` MDX по стандарту — **с уникальным набором/порядком блоков и своим визуалом** (не повторять предыдущие статьи).
5. `npm run build` — убедиться, что собирается.
6. `npm run audit:blog` — **должно быть 0 ERROR** (хук всё равно проверит на push).
7. Коммит и push (pre-push аудит запустится). По желанию `npm run indexnow`.

## 10. Definition of Done
- [ ] ru + en версии, уникальный дизайн (не как у других статей)
- [ ] **≥1200 слов** на язык (лонгрид)
- [ ] hero + ≥2 фото (аутентичные, просмотрены), **фото нигде не повторяются**, hero — другой категории
- [ ] ≥1 уникальная инфографика/визуал
- [ ] ≥5 FAQ в теле, 2–3 inline-CTA
- [ ] факты из Tier-1 + источники + даты
- [ ] правильный автор по теме
- [ ] **`keyword` задан**; ключ в `title` и в первом абзаце `<Lead>`
- [ ] **≥3 внутренних ссылки** на родственные статьи (блок «Похожие статьи», en — с `/en/`); статья не «сирота»
- [ ] **AEO:** есть `<KeyTakeaways>` (TL;DR с числами) + **≥1 H2-вопрос** (`## …?`); Lead начинается с прямого ответа (BLUF)
- [ ] **карточка /blog:** `image`+`imageAlt`, `cluster`=C1–C13 (тег виден), `dateModified` = дата этой правки
- [ ] **верхний блок (hero) виден полностью**, не перекрыт фикс-хедером (top-padding pt-32+)
- [ ] **подложка меню сплошная** (как на главной), лого читается на любом hero
- [ ] `npm run audit:blog` = **0 ERROR и SEO-score ≥70 (цель ≥85)**

## 11. Фактические инварианты (консистентность по корпусу)
- **ИП для иностранца:** не писать «ИП иностранцу недоступен» плоско. Каноничная формулировка: *ИП доступен иностранцу только при проживании в Узбекистане (регистрация по месту жительства/ВНЖ) и с ограничениями — поэтому нерезиденту проще ООО/иностранное предприятие.* Со ссылкой на `/blog/ip-v-uzbekistane-dlya-inostrancev`. Эталон фактов по теме — эта статья.
- Любую цифру/ставку/срок сверяй с уже опубликованными статьями кластера, чтобы не было противоречий между материалами.
